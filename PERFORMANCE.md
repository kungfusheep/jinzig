# jinzig performance

The detail behind the [README](README.md)'s summary: how the numbers are made, every table, and what explains them.

## Before reading the numbers

- **jinzig only escapes strings when a field asks** (`,escape`), as jingo does. Every other library escapes every
  string, every time. The *like for like* table below is the default suite; the *escaping every string* table turns
  `,escape` on for every jinzig string field, and is the fair comparison.
- **The payloads are jingo's**: mostly strings and ints, few floats, nothing that needs escaping in the default
  suite. jinzig formats floats through `std.fmt` like the others, so float-heavy documents narrow the gap.
- **These are microbenchmarks**: one payload in a hot loop, with warm caches and trained branch predictors.
- **Zig's JSON encoders are young.** None has had the years of competitive tuning Go's have had, while jinzig
  inherits a design that was tuned against Go's fastest. That, more than anything clever, is why the gaps are large.

## Method

Apple M5 Max, macOS, Go 1.27.1, Zig 0.17.0 `ReleaseFast`, `./bench.sh`. Inputs are the jingo_test.go payloads.

Before a library is timed on a payload, the harness checks its output against jinzig's document, which the tests
pin to jingo's golden output. A library that emits anything else is marked ✗ and not timed. The one accepted
divergence is std.json, which writes the `f32` field with f64 precision.

## Reading the numbers

- **Write runs:** the plan groups each run of keys, plain strings and plain ints into one write. A run adds up its upper bound (the static bytes, 20 per int and the string lengths), reserves it with one capacity check, writes through a cursor held in a register and sets the length once. Updating the buffer's length on every write was the real cost: a byte store may alias it, so each write had to reload it and wait on the last one. A slice of plain or nullable strings (Json's 269-element `ps`), or of structs that are one run (LargePayload's users and topics), reserves once for every element.
- **No dispatch loop:** jinzig began as a faithful port with jingo's runtime instruction loop. Unrolling the same plan at comptime ran up to 4.8x faster (level on Time and SliceEscape), and setting up the interpreted encoders grew exponentially with nesting (one encoder per field occurrence, as in jingo), so the loop was removed.
- **yyjson:** fast C, but built around a document: every value is a node allocated from the pool and linked into
  the tree, and the writer then walks it. Timing the writer alone on a built document (by writing it ten times)
  puts it at about 33 ns for SmallPayload and 1,390 ns for LargePayload, with the build making up the rest. That's
  already slower than jinzig escaping every string, which writes field by field and never builds a document.
- **vs the other Zig encoders:** they reflect over fields at comptime too, but still decide commas and colons at runtime, re-escape constant keys on every call, scan every string, and format ints through `std.fmt`. jinzig makes those decisions when the encoder is compiled, and only escapes when a field opts in.
- **Escaping:** `,escape` screens 32 bytes per iteration with three vector compares (`"`, `\`, `< 0x20`) and one reduce. Only flagged blocks get the exact five-byte check, out of line, and the end of the string is covered by an overlapping block. Strings under 16 bytes use overlapping SWAR word loads. A clean string is one check plus one copy.
- **Closest rivals:** with every string escaped, yyjson is closest on Json and Slice (1.2x and 1.5x behind) and lalinsky/json.zig (comptime-specialised like jinzig) on the rest (1.3–2.7x). On Time, jinzig and lalinsky both spend most of it formatting the date and are within 18%. In the default suite jaysan, which never escapes, comes closest on long strings.
- **Writer cost:** `std.Io.Writer`'s hot path is non-virtual (bounds check plus `memcpy`). A microbenchmark of the SmallPayload write sequence measured it about 11% slower than jinzig's `Buffer` when inlined, and about 28% slower across a non-inlined call. That's small next to the gaps above.
- **Short copies:** field values up to 64 bytes are copied with overlapping word or vector stores instead of a libc `memcpy` call, ints are written straight into the output two digits at a time, and comptime-known chunks use fixed-size stores.
- **Allocation:** zero allocations at steady state, and profiles show no allocator time in the hot loop. A test encodes a twelve-level nested type with an allocator that fails on any request.

## Running them

```sh
./bench.sh                          # go jingo vs jinzig vs the zig encoders -> results/, README.md, PERFORMANCE.md
                                    # (COUNT=3, BENCHTIME_MS=300 by default; nothing allocates, so that's plenty)
bench/third_party.sh                # fetch the other encoders at pinned commits (bench.sh does this on first run)
zig build test -Dcompetitors=true   # also verify the other encoders emit jingo's documents byte for byte
tools/profile.sh Esc/UnicodeLarge/jinzig   # Instruments Time Profiler -> flame graph svg + self-time summary
```
